## Contract Changes
- GET /users/<id>, POST /users, PUT /users/<id>, POST /login: campo `password` removido (de `user` no login) — motivo: AP-04
- POST /login: `token` passa a ser assinado (itsdangerous) e expira em SESSION_TOKEN_MAX_AGE; o antigo `fake-jwt-token-<id>` deixa de existir — motivo: AP-06
- POST /tasks: 401 sem `Authorization: Bearer <token>` válido — motivo: AP-06
- PUT /tasks/<id>, DELETE /tasks/<id>: 401 sem token válido; 403 se não for o dono da task nem admin — motivo: AP-06
- PUT /users/<id>, DELETE /users/<id>: 401 sem token válido; 403 se não for o próprio usuário nem admin; `role`/`active` só por admin (403) — motivo: AP-06
- POST /users: `role` diferente de `user` exige admin (403) — motivo: AP-06
- POST/PUT/DELETE /categories: 401 sem credencial; 403 para não admin — motivo: AP-06
- POST /tasks e PUT /tasks/<id> (priority/título/ids/tags de tipo errado), GET /tasks/search (priority/user_id não numéricos), PUT /categories/<id> (corpo ausente/null): 500 → 400 com mensagem — motivo: AP-15/AP-14
- POST/PUT /categories: `color` fora do formato `#RRGGBB` → 400 "Cor inválida"; PUT /users: `name` vazio → 400, `active` não booleano → 400 — motivo: AP-15
- Todas as rotas: 404/405/500 e corpo JSON inválido respondem `{"error": ...}` em JSON (antes HTML) — motivo: AP-14
- CORS: desligado por padrão; liberado só para as origens de CORS_ORIGINS (antes qualquer origem) — motivo: AP-16

## Pending
- AP-09 (órfãos em DELETE /categories): a execução mostrou que o ORM já desassociava as tasks (passo 44 com `category_id: null` antes e depois); a parte de "órfãos" do finding não se confirmou. A desassociação agora está explícita no serviço, sem mudança de comportamento.
- NotificationService: refatorado (config e cliente SMTP injetados, criado no composition root) mas não está ligado a nenhuma rota, como no original. Ligar à atribuição de tasks é decisão de produto.
- Política de senha: o mínimo de 4 caracteres foi mantido para não quebrar o contrato. Recomendação: subir para 8 ou mais.
- Bancos já existentes com hashes MD5 não são migrados (fora do escopo): esses usuários precisam redefinir a senha ou rodar `python seed.py` de novo.
- Refresh/revogação de token e rate limiting no /login: fora do escopo (guidelines §5).
- Sem SECRET_KEY no ambiente, a chave é temporária e os tokens deixam de valer a cada reinício. Defina SECRET_KEY no .env.
- Leituras públicas (GET /users, /users/<id>, /reports/*) continuam abertas e listam e-mails, porque a recomendação não pedia proteção. Avaliar exigir token.
- `python seed.py` com PYTHONWARNINGS=default emite um ResourceWarning de conexão SQLite não fechada ao sair do processo (script de CLI, sem impacto na API).
